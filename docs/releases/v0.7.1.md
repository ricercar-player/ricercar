## What's fixed

- **Streams from servers that send many headers play again.** Some content delivery networks answer with more than 100 HTTP headers, which the previous HTTP library refused, so those tracks were skipped as unplayable, now and then. Streams now go through ricercar's own HTTP client, which accepts up to 512 headers and keeps everything that worked: seeking with Range requests, internet radio titles, streams of unknown length, redirects.
- **Clearer errors.** A stream that fails now says why (too many headers, malformed response, TLS error, timeout) instead of "unsupported source".
- **No secrets in the log.** Stream addresses in the log, in error messages and in the diagnostic report keep their host and path but not the values of their query (`?token=…`), which often carry account identifiers or signatures.
- **The playing track is marked on plugin pages.** Album and playlist pages from a plugin now highlight the track being played, like local ones.

## For plugin authors

- Stream URLs are fetched over HTTP/1.1 without compression; redirects are followed (at most 5, never from https to http); responses may carry up to 512 headers. See [docs/plugins.md](https://github.com/ricercar-player/ricercar/blob/v0.7.1/docs/plugins.md).
- Lines your plugin writes to stderr are logged with the query values of any URL masked.
